## 삼삼엠투: 6종 매물 수집 수정 + DB 배치 픽스 + 로컬 크롤 GUI(.exe)

### 1. 매물 종류 6종 전부 수집 (crawler.py)
- 사용자 요청: 오피스텔·아파트·연립빌라·단독주택·원룸건물·상가주택 전부 수집.
- 원인: `PROPERTY_TYPES`가 죽은 코드(`HOUSE/STORE/OFFICE`)를 써서 3종이 0건이었음.
  API를 직접 조회(필터 없이 목록 → propertyType 한글값 집계, 코드별 건수 확인)해 실제 코드 확정:
  - 단독주택 `HOUSE`→`DETACHED`, 원룸건물(신규) `STUDIO`, 상가주택(신규) `MIXED_USE`.
  - 확정: `['OFFICETEL','APARTMENT','VILLA','DETACHED','STUDIO','MIXED_USE']`.
- 참고: 목록 API의 `room['propertyType']`은 한글 라벨, 필터 쿼리 `propertyTypes=`는 영문 코드 — 서로 다름.
- 결과: 수도권 대상 ~10,900 → ~16,600건. 신규 수집 대상 ~42 → ~5,700건(단독/원룸/상가 백필).

### 2. db.py executemany 트랜잭션 픽스
- 증상: 신규 대량 적재 시 `pg8000 ... unnamed prepared statement does not exist`(SQLSTATE 26000).
- 원인: `autocommit=True` 상태로 executemany → Supabase 트랜잭션 풀러(pgbouncer)가 문장 사이
  백엔드를 갈아끼워 unnamed statement 소실. (신규 42건일 땐 우연히 안 걸렸음.)
- 수정: pg8000 executemany를 명시적 트랜잭션으로 감싸 한 백엔드에 고정. 확인 후 정상 적재(시도50/100…).

### 3. GitHub Actions 삼삼 크롤 실패 원인 규명
- `crawl-samsam.yml`이 5일 연속 실패(21:00 UTC 스케줄). 로그: 로그인·목록수집은 성공하나
  예약률 갱신에서 스케줄 API가 HTTP 200(`ok`)+빈배열 → 두 계정 첫 요청부터 데이터0 → `exit 1`.
- 결론: 크롤러 버그 아님. **GitHub 호스티드 러너(미국 데이터센터 IP)에 대한 삼삼의 소프트차단**.
  같은 계정으로 로컬(한국 IP)에서는 정상 수집됨(대조 확인). GHA에서 예약률 갱신은 구조적으로 불가.
- 대안: (A) 셀프호스티드 러너(한국 IP), (B) 로컬 수동, (C) 프록시. → 사용자와 (A)/GUI 방향 논의.

### 4. 로컬 크롤 GUI (.exe) — gui/rendit_crawler.py + common/local_db.py
- 사용자 요청: 버튼 누르면 창 뜨고 크롤하는 프로그램. 접속정보는 입력창에 기입. DB 대신 로컬 폴더 누적도 선택.
- tkinter GUI: 삼삼 계정 2개·매물종류 체크박스·테스트(50건)·실시간 로그. 입력값은 옆
  `rendit_crawler_config.json`에 저장. 파이프라인(crawler→snapshot→export)을 in-process 호출.
- **저장 위치 선택**:
  - Supabase(DB URL) 또는 **로컬 폴더(SQLite)**. 로컬은 `common/local_db.py`를 `sys.modules['db']`로
    주입해 크롤러가 그대로 선택 폴더의 `samsam.db`에 upsert 누적 + jsonl도 그 폴더에 export.
  - local_db는 samsam 크롤러의 PG 방언을 SQLite로 흡수: `%s`→`?`, `ON CONFLICT ... EXCLUDED`(SQLite 지원),
    `ALTER ... ADD COLUMN IF NOT EXISTS`(중복 무시), 행은 `r[0]`/`r['col']`/`r.get()` 모두 지원.
  - 오프라인 단위검증 통과: init→ALTER→upsert(%s+ON CONFLICT)→SELECT→snapshot→export, 폴더에 db+jsonl 생성.
- PyInstaller onefile+windowed 빌드(~60MB). 크로미움은 번들 안 하고 PC 설치본 사용(다른 PC는 첫 실행 시
  `playwright install chromium`). 프로즌 exe에서 `--selftest`(모듈/경로/의존성) PASS.
  ※ 실제 [크롤 시작] 클릭(크롬 로그인) 런타임은 GUI라 미검증 — 로컬 크롤과 동일 코드경로.
- 배포물은 bytes 커서 채팅 첨부 불가 → 바탕화면 `삼삼크롤러.exe`로 전달.

## 네이버 부동산 수도권 7종 재크롤 + 사이트 진짜 실시간 반영 (feature/realtime-listings-view)

### 크롤 범위·유형

- 지역 **서울/경기/인천만**, 매물유형 **7종 월세(B2)**: 아파트(APT)·오피스텔(OPST)·빌라(VL)·
  원룸(OR)·단독다가구(DDDGG)·상가(SG)·**전원주택(신규 JWJT)**.
- `crawler.py`: TYPES에 `JWJT` 추가(라이브 검증). 버그 2건 수정:
  1. `regions`에 과거 비수도권 전국 동이 섞여 `--sido` 미지정 시 강원도까지 긁던 것 →
     **ROOTS(수도권)만** 필터(3856→1370동).
  2. 로컬 Python 3.15라 psycopg2 휠 없음 → pg8000이 Supabase 풀러 6543(트랜잭션)에서
     prepared statement 깨짐(26000/08P01). 크롤은 **5432(세션 모드)** URL로 실행해 해소.
     (삼삼 세션의 db.py executemany 트랜잭션 픽스와 동일 원인 — 이쪽은 접속 URL로 회피.)
- crawl_state 리셋 후 7종 재크롤. 상세 크롤은 재시작 루프로 감싸 일시 DNS 오류에도 이어받게 함.

### 사이트 진짜 실시간 반영

- 문제: 사이트는 상세보강 `naver_listings`를 읽는데 상세 크롤이 매물당 API 3~4회라 느려
  (상가 20만+ → 30시간+) 한 번에 반영됨. 요청 = 실시간.
- 해법: **실시간 뷰 `nl_live`**(`pipeline/naver/create_live_view.py`).
  `listings`(실시간·수도권·최근7일) LEFT JOIN `naver_listings`(상세). 목록 크롤이 넣는 즉시
  사이트에 뜨고 상세는 채워지는 대로 자동 병합. 필터/정렬/집계 컬럼은 listings 직접 노출(인덱스),
  상세 전용(rooms·floor·subway·주소)만 조인. **7일 신선도**로 내려간 매물 자동 숨김(DB엔 유지).
- `web/gangnam_app.py`: 조회 소스 `naver_listings`→`nl_live`, 기본정렬 `crawled_at DESC`(인덱스),
  타입에 전원주택 추가(상가 제외 해제=7종 전부), 상세모달 nl_live 폴백, 집계는 짧은 TTL 캐시 +
  facets sido는 regions 테이블에서(전체 스캔 회피). listings에 인덱스 5종 추가.
- 검증: test_request_context로 전 API 실측 — 필터/상세/폴백 정상, warm 0~200ms.
  (무필터 전체 count는 크롤 동시 INSERT 부하로 cold 느림 → 크롤 종료 후 개선. count 캐시 60s.)
- 정책(사용자 확정): 사이트 표시 **7종 전부**, 신선도 **최근 7일**만 노출·과거는 DB 유지.
