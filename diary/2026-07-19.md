## Oracle Cloud 프로덕션 배포 — https://rendits.duckdns.org (웹 세션)

"서버가 전반적으로 느리다" 진단(7/17)에서 출발: 주범은 Vercel(미국 iad1)↔Supabase(서울) 태평양
왕복(페이지 ~1초) + 서버리스 콜드스타트. kv_cache precompute(#224)로 20초 재계산은 없앴지만
왕복 자체는 리전 문제 → 팀원의 Oracle Cloud Free VM으로 이전.

### 서버 스펙 (팀원 제공, ubuntu@158.179.170.9)
- **ap-chuncheon-1(춘천!)** · VM.Standard.A1.Flex — ARM Ampere 4코어(Neoverse-N1)·**24GB RAM**·194GB
- Supabase(서울) TCP 왕복 **54ms** (Vercel 대비 ~20배 단축). 기존 팀원 서비스 starec2(포트 13999/42257)
  가동 중 — 안 건드림. iptables는 비어있고 정책 ACCEPT → 방화벽은 OCI 보안목록(콘솔)만.

### 배포 과정
1. paramiko(SSH)로 원격 작업. Docker 29.6.2 설치(get.docker.com), STA clone, .env SFTP 전송.
2. `docker compose up -d --build` — ARM64 빌드(python:3.11-slim 멀티아키 확인). 내부 응답 **3.5ms**.
3. OCI 보안목록: 팀원에게 최소개방 원칙 메시지 전달(80/443만, 예비포트는 안티패턴이라 제외,
   5432 금지, SSH 비번노출 경고 포함). 개방 후 80으로 재매핑(docker-compose.override.yml,
   `ports: !override`).
4. **Postgres 17 컨테이너**(pg, 도커 네트워크 내부 전용·포트 미노출·비번은 서버 .env에만) 가동.
   Supabase→로컬 복사는 가드레일로 사용자 승인 대기 중. (첫 시도 실패 원인: `source <()`는 bash 전용
   — sh에선 빈 값. `$(grep|cut)` 방식으로 해결.)
5. **DuckDNS**: 사용자가 rendits.duckdns.org 생성 → 스크린샷의 토큰으로 API IP 설정. DNS 확인.
6. **Caddy 2**(caddy:2-alpine) 리버스프록시: 처음엔 http 직접 서빙(443 미개방 대비)으로 올렸는데
   Let's Encrypt가 tls-alpn-01(443)로 검증 성공 → 443도 열려 있었음. 인증서 자동 발급 확인 후
   표준 구성 전환: https 서비스 + http/IP → https 리다이렉트(308/301).

### 결과
- **https://rendits.duckdns.org — 35~55ms** (Vercel 913~1134ms 대비 ~25배). 콜드스타트 0.
- 로그인·대시보드(스팟 16카드)·profit/map_all API 전부 정상, JS에러 0.
- restart:unless-stopped — 재부팅·크래시 자동 복구. Vercel은 백업으로 유지(main push 자동배포 계속).
- 접속정보는 C:/STA/.env(ORACLE_HOST/USER/PASSWORD, RENDIT_DOMAIN)에 저장.

- 크롤러를 이 VM(한국 IP!)으로 이전하면 삼삼 GHA 미국IP 차단 문제도 해결 — 추후.

- 보안: SSH 비번 채팅 노출 → 팀원에게 변경/키전환 요청함. DuckDNS 토큰도 스크린샷 노출(재발급 권장).

### Supabase → 서버 pg 복사 (완료)
- 사용자 승인 후 실행. 487MB 덤프 → listings 712,073 / naver_listings 197,800 / samsam_listings
  22,410 / net_profit 17,219 등 전 테이블 행수 검증 일치.
- **함정 기록**: ①pg_dump에 URI를 직접 주면 "database postgres does not exist" — 반드시 컴포넌트
  (-h/-p/-U/-d + PGPASSWORD)로. ②복원 docker exec에 --env-file을 주면 PGHOST(Supabase)가 새어
  들어가 복원이 조용히 원격을 향함 — 복원·검증은 env 주입 없는 깨끗한 exec로.

### 카카오 로그인 KOE101 (원인 파악, 사용자 작업 대기)
- 카카오 키가 Vercel 환경변수에만 있고 로컬/서버 .env엔 없음 → 빈 client_id로 KOE101.

### 크롬 "위험한 사이트" 경고 (Google Safe Browsing)
- duckdns.org 공유 도메인 평판 문제(피싱 단골 도메인). 사이트 자체 문제 아님.
- Search Console 소유권 확인용 TXT를 DuckDNS API로 등록(사용자 실행), 8.8.8.8에서 조회 검증 완료.
- 근본 해결은 자체 도메인 구입 권고(rendit.kr 등).

### 팀원 문의 "부동산 매물 데이터가 안 받아와짐" → 진단·전환 준비
- 원인: ①/gangnam은 로그인 필수(비로그인 API가 302→로그인) ②로그인해도 listings 27초/stats 37초.
- 병목 = Supabase 쿼리 실행 자체(COUNT(nl_base) 11.3s). **동일 쿼리가 서버 내부 pg에선 0.3s(~90배)**.
- 전환 스크립트를 deploy/에 커밋: cutover_env.py(.env 수리+DATABASE_URL 전환·멱등),
  apply_cutover.sh(비번정렬→전환→재시작→크론), sync_from_supabase.sh(6시간마다 크롤 데이터
  테이블만 Supabase→로컬, 회원·채팅은 로컬 원본이라 불가침), backup_users.sh(사용자 테이블 매일 백업).
- 중간에 서버 .env의 LOCAL_PG_PASSWORD가 이전 줄 끝에 붙어 5자 잘려 있던 것 발견·수리.
  1차 전환 시도는 이 때문에 비번 불일치 500 → 즉시 Supabase로 롤백(서비스 복구 확인).
- 비밀번호 조작 명령이 CLI 보안 분류기에 막혀 최종 적용은 사용자가 ssh 한 줄로 실행하기로.

### 지도 개선 — 네이버지도식 동/시군구 건수 뱃지 (사용자 요청)
- 렌트 레이어 줌아웃 시 supercluster의 임의 "n개" 뭉침이 거슬린다는 피드백 →
  줌 12~14는 실제 동 단위, 12 미만은 시군구 단위 건수 뱃지(보라 필, 건수+지역명)로 교체.
- 줌 15+만 개별 핀(supercluster는 같은 지점 겹침 정리용으로만 유지). 뱃지 클릭 = 60건 이하면
  목록 모달, 많으면 해당 지역으로 줌인. 동별 예약률 점·배지와 안 겹치게 지점 위로 오프셋.
