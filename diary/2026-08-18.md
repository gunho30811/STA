# 2026-08-18

## 통합채팅 공급자 확장 준비 — 리브애니웨어 정찰 (A단계, 인증 전 공개 정찰)

배경: 현재 통합채팅은 **삼삼엠투 단일 공급자**. 리브애니웨어를 추가하려고 정찰부터 시작.
범위는 **수신 + 카톡 알림만 우선**(답장은 후속)으로 결정 — 삼삼에서 제일 까다로웠던
`/host/chat` UI 자동화·오발송 방지가 이 단계엔 불필요.

### 현재 결합도 (삼삼 하드코딩 지점)
- `common/chat_auth.py` — 전부 삼삼 전용: Firebase(RTDB `spacev-33m2-rdb`)·`web.33m2.co.kr`·
  Firebase API 키·`live/chatlist/{member_id}`·`live/messagelist/{room_key}`·`/host/chat` UI.
- `common/chat_poll.py` — `chat_auth`를 직접 호출, 삼삼 데이터 형태(`host_or_guest`·`member`·
  `room_key`) 가정. DB 테이블 `samsam_accounts`/`samsam_chat_rooms`/`samsam_chat_messages`.
- 웹 라우트 `/samsam/chat` (samsam_app).
- `kakao_notify` 는 공급자 무관 — 그대로 재사용 가능.

### 정찰 결과 (인증 없이 공개 사이트 Playwright 로드 + 네트워크/전역 관찰)
- **host.liveanywhere.me** = **아임웹(imweb) 기반**. 전역 `__fo-chat__` + 요청
  `GET /_/fo-chat/index.magnet.json`(imweb 내장 채팅 위젯), `/ajax/oms/OMS_auth.cm`(imweb OMS 인증).
  Firebase(analytics·installations, project=`liveanywhere-live1month`)도 로드하나 분석용으로 보임.
- **console.liveanywhere.me** = **Next.js 호스트 콘솔**. 미로그인 시 `account.liveanywhere.me`(SSO)로
  리다이렉트. 관측된 핵심 호출: **`POST https://api-gateway.liveanywhere.me/v1/refresh-token`**
  → **자체 REST API 게이트웨이 + JWT(access/refresh)** 구조. Sentry·Airbridge 사용.
- **account.liveanywhere.me** 로그인 = **카카오 / 구글 / 이메일·휴대폰** (소셜 + 이메일).

### 삼삼과의 핵심 차이
- 삼삼: 순수 **Firebase**(로그인=커스텀토큰, 갱신=securetoken, 조회=RTDB REST).
- 리브애니웨어(콘솔): **자체 api-gateway REST + JWT**. 단 "브라우저 로그인 1회 → 이후 HTTP 갱신"
  패턴은 동일(리프레시 엔드포인트 `v1/refresh-token` 존재 확인) → 폴링은 브라우저 없이 가능할 것.

### 채팅 백엔드 후보 (⚠ 미확정 — 로그인 후 정찰 필요)
1. **console = api-gateway REST 폴링** (유력) — 방/메시지 조회 엔드포인트(`v1/...`)를 authed로 찾아야 함.
2. **host = imweb fo-chat** — 임대인이 게스트 문의를 이쪽(아임웹 내장 채팅)에서 받는 경우.
   실제 호스트가 문의를 **어느 surface에서 받는지** 확인이 최우선.

### Provider 추상화 계획 (구현 시)
- 공통 인터페이스: `login(email,pw)` → `refresh(token)` → `list_rooms` → `list_messages` (→ `send` 후속).
- `chat_auth.py` → `common/providers/samsam.py` 로 분리, 출력(방/메시지)을 공통 형태로 정규화.
- `chat_poll.py` 가 `account.provider` 로 분기 → 삼삼/리브애니웨어 각 구현 호출.
- DB: `samsam_accounts` 에 **`provider` 컬럼 추가**(기본 `'samsam'`), `samsam_room_key`/`samsam_member_id`
  의미 일반화(테이블명은 우선 유지, 혹은 `chat_accounts`로 리네임은 후속 판단).
- 웹 계정연결 폼·통합 인박스에 공급자 배지 표시.

### 다음 단계 (인계 — 다른 세션/PC에서 이어서)
1. **리브애니웨어 host 계정 확보**(실제 문의 채팅이 오가는 임대인 계정) → 로그인 흐름·JWT 캡처 위치
   (localStorage/응답 바디)·채팅 API/저장소 확정. `.env`에 안전 저장.
2. 게스트 문의 수신 surface 결정: **console(api-gateway REST) vs host(imweb fo-chat)**.
3. `common/providers/liveanywhere.py` 구현(login→refresh→list_rooms→list_messages).
4. DB `provider` 컬럼 마이그레이션 + `chat_poll` 분기.
5. 웹 계정연결/인박스 공급자 구분.

> 이 커밋은 **정찰·설계 기록만**(코드 변경 없음). 실제 구현은 host 계정 확보 후 진행.

## (이어서) authed 정찰 — 리브애니웨어 채팅 = **Sendbird** 확정

`.env`에 `LIVEANYWHERE_EMAIL`/`LIVEANYWHERE_PASSWORD`(host 계정) 넣고 실제 로그인해 정찰 완료
(라건호 / 호스트번호 36174 — **대화 0건인 빈 계정**). 토큰 값·비번은 로그에 안 남김.

### 확인된 아키텍처 (실동작)
- **로그인**: `POST api-gateway.liveanywhere.me/v3/sign-in`(이메일+비번) → 응답은 `{succeed:true}`만.
  **JWT는 응답 바디가 아니라 httpOnly 쿠키로 세팅**(localStorage에 토큰 없음, Authorization 헤더도 안 씀).
  로그인 폼은 단일 페이지(이메일/휴대폰 + 비번, **OTP 없음**) — Playwright 자동화 문제없음.
- **세션 갱신**: `POST api-gateway.liveanywhere.me/v1/refresh-token`(쿠키). → 폴러는 **쿠키 세션
  (`requests.Session`)** 방식. 삼삼(Firebase idToken)과 다름.
- **메시지 라우트**: 콘솔 좌측 nav "메시지" → `/chat/channels/host` (SPA 클라이언트 라우팅).
  직접 URL `/chat` 등은 404.
- **채팅 백엔드 = Sendbird**: 메시지 페이지가 **`GET api-gateway.liveanywhere.me/v1/sendbird/my-channels`**
  호출. 삼삼(Firebase RTDB)·자체 DB 아님. **브라우저→Sendbird 직접 트래픽 없음 → api-gateway가
  Sendbird를 프록시**(쿠키 인증으로 채널 목록 조회 → Sendbird SDK/토큰 불필요일 가능성 높음).
- `my-channels` 응답 포맷: `{success, code, message, meta:{pageNumber,pageSize,totalPageCount,
  totalResultCount}, body:[...], errorCode}`. 빈 계정이라 `body:[]`.
- 부가: `GET /v1/hosts/me/unread-message-count`(안읽음 수), `GET /accommodation/v1/auto-messages/my`
  (호스트 자동메시지 — 채팅 아님).

### 삼삼 vs 리브애니웨어 (요약)
| | 삼삼엠투 | 리브애니웨어 |
|---|---|---|
| 채팅 백엔드 | Firebase RTDB | **Sendbird (api-gateway 프록시)** |
| 로그인 | 이메일+비번(Firebase 커스텀토큰) | 이메일+비번 → `v3/sign-in` |
| 인증 유지 | idToken(Bearer, securetoken 갱신) | **httpOnly 쿠키 세션**(`/v1/refresh-token`) |
| 방 목록 | RTDB `live/chatlist/{id}` | `GET /v1/sendbird/my-channels` |

### 수신+알림 MVP 경로 (확정)
로그인(쿠키) → `/v1/sendbird/my-channels` 폴링 → 채널별 last_message/unread 변화 감지 → `kakao_notify`.
삼삼의 RTDB 다중 조회 대신 **이 한 엔드포인트**로 충분할 전망(브라우저는 최초 로그인 때만, 이후 순수 HTTP).

### 마지막 블로커 & 다음
- 이 계정은 **대화 0건**이라 **채널 item 필드(channel_url·last_message·unread·상대 닉네임·시각)를
  실데이터로 아직 못 봄**. → 실제 문의 1건 있는 계정으로 1회 확인하거나 Sendbird 표준 스키마로 확정.
- 메시지 본문 읽기가 api-gateway 프록시인지 Sendbird 직접인지도 그때 확인(수신+알림만이면 my-channels로 충분할 수도).
- 그다음: `common/providers/liveanywhere.py`(login 쿠키 / refresh / list_channels) → DB `provider` 컬럼
  → `chat_poll` 분기 → 웹 계정연결·인박스 공급자 배지. (답장은 후속 — Sendbird 전송 경로 필요.)

> **상태: 로그인·세션·채널목록 엔드포인트까지 실동작 확인 완료.** provider 구현 준비됨(필드 매핑만 실데이터로 확정).

## 통합채팅 계정 연결에 **공급자 선택** 추가 (삼삼엠투 / 리브애니웨어)

provider 추상화의 첫 단추 — 계정 연결 시 공급자를 고르게 하고 계정에 귀속. (수신 폴러 구현은 후속)

- **DB**(`db.py`): `samsam_accounts`에 `provider TEXT DEFAULT 'samsam'` 컬럼 추가(CREATE + 멱등 ALTER).
  기존 계정은 DEFAULT로 자동 `'samsam'` — 삼삼 동작 불변.
- **웹**(`web/samsam_app.py`):
  - `chat_api_add_account`: `provider`(samsam|liveanywhere) 검증·저장. **리브애니웨어는 삼삼 로그인
    (33m2)을 절대 시도하지 않고** 자격증명만 암호화 저장 + `status='pending_provider'`(연동 준비 중)로
    큐잉 → 폴러/공급자 구현 완료 시 자동 활성화.
  - `chat_api_accounts`: 응답에 `provider` 포함(인박스 배지용).
  - `chat_api_poll`(수동 폴링): `provider='samsam'`만 대상.
- **삼삼 폴러**(`common/chat_poll.py` `poll_all`): `provider IS NULL OR 'samsam'`만 폴링 —
  리브애니웨어 계정에 삼삼 로그인 시도 방지(오작동·reauth_needed 오표시 차단).
- **프론트**(`frontend/src/chat/AccountsPanel.jsx` + `styles.css`): 계정 연결 폼에 **공급자 드롭다운**
  (삼삼엠투/리브애니웨어) 추가, POST에 `provider` 포함, 계정 카드에 공급자 배지. `npm run build:chat`로
  `frontend/dist/chat` 재빌드(커밋 포함).
- 검증: py_compile 통과, vite chat 빌드 성공. 삼삼 경로는 provider 기본값이라 회귀 없음.
- 남은 것: `common/providers/liveanywhere.py`(login 쿠키/refresh/list_channels) 구현 시
  `pending_provider` 계정을 실제 폴링 대상으로 승격.

## init_db 마이그레이션 누락 버그 조사·수정 (배포 중 발견)

provider 컬럼 배포 시 **운영 DB에 컬럼이 안 생겨** 수동 ALTER로 급히 반영했는데, 원인을 파봤음.

- **원인**: `init_db()`에 '기존 DB 빠른 경로'(members 테이블 존재 시)가 있는데, **하드코딩된 ALTER
  4개만 돌리고 early return**했음. 본문 CREATE/ALTER 구간은 기존 DB에선 아예 실행 안 됨 →
  본문에 추가한 `provider` ALTER가 운영 DB에 절대 반영되지 않았던 것(콜드스타트 락 회피용 최적화의 부작용).
  autocommit 연결이라 트랜잭션 문제는 아니었고, **순전히 early return 이 원인**.
- **수정**: 모든 `ADD COLUMN IF NOT EXISTS`(14개)를 **`_COLUMN_MIGRATIONS` 단일 목록**으로 모으고,
  `_run_column_migrations(conn)`을 **빠른 경로(기존 DB)·전체 경로(신규 DB) 둘 다**에서 실행.
  본문에 흩어져 있던 인라인 ALTER는 전부 제거(단일 출처). 개별 실행+예외 격리라 한 문장이 실패해도
  나머지는 진행. → **앞으로 새 컬럼은 `_COLUMN_MIGRATIONS`에만 추가하면 배포 시 자동 반영.**
- 검증: py_compile 통과. 배포 후 컨테이너에서 init_db 재실행해 14개 컬럼 존재 확인 예정.
