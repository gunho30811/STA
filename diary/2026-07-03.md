## 삼삼 예약률 갱신 — 공실 우선 로테이션 + 조기 중단 즉시 종료 (fix/samsam-vacancy-priority-rotation)

전날(7/2) "삼삼엠투 크롤링 자동화(매일)" 스케줄 run이 실패해 원인 추적.

- **실패 원인**: 코드 버그가 아니라 안전장치 정상 동작. 예약률 갱신 초반 200건에서 서버가
  HTTP 200(ok)은 주는데 스케줄 데이터는 0건으로 응답 → 소프트차단으로 판단해 DB 미반영·`exit 1`
  (4b16e04에서 넣은 0 오염 방지 로직). PR #72(현재접속자수)는 Vercel 통과로 무관.
- **로그의 이상점 = 30분 공백**: 22:20 차단 판단 후 종료가 22:50. 원인은 `REFRESH_CHUNK=2000`건을
  ThreadPool에 한 번에 submit → 200건에서 `break`해도 `with ThreadPoolExecutor` 종료가 제출된
  ~1800건이 다 끝날 때까지(2워커+20초 쿨다운) 블로킹. **→ `try/finally`로 바꿔 조기 중단 시
  `pool.shutdown(wait=False, cancel_futures=True)`로 미시작 요청 취소, 30분 대기 제거.**
- **공실 우선 로테이션**(사용자 제안): 이미 한 달치 예약 잡힌 매물은 매일 다시 봐도 안 바뀜.
  `booked_days_1m>0`이면 마지막 확인 후 `BOOKED_COOLDOWN_DAYS`(기본 7, env 조정)일 동안 재갱신
  제외, 공실은 매 실행 갱신 → 하루 5000건 예산을 '새 예약이 잡히는' 공실+쿨다운 경과분에 집중.
  쿨다운 지난 예약 매물은 다시 대상에 들어와 취소/연장도 반영. `collected_at`(=마지막 확인 시각)
  ISO 문자열 비교로 판정.

## 건물 인기 탭 — 오피스텔(건물명) 검색 + 자체 검색 색인 모듈 (feature/building-name-search)

건물 인기 탭에 건물명(오피스텔 명) 검색을 추가하면서, 검색 로직을 별도 `search/` 패키지로 분리.

- **엔진 선택**: Elasticsearch 검토했으나 제외 — 우리 배포가 Vercel 서버리스(상주 서버 없음,
  읽기전용 FS)라 ES는 외부 클러스터(월과금)가 필요하고, 데이터가 적어(수만 건) 가치 대비 과함.
  SQLite FTS5(trigram)도 검토했으나 **trigram 토크나이저가 3자 미만 질의를 못 잡음**("강남"·
  "한화" 같은 2자 한글 검색이 빈 결과) → 실측 확인 후 탈락.
- **결정**: 외부 엔진 없이 **순수 파이썬 n-gram(기본 2-gram) 역색인**을 직접 구현(`search/`).
  2자 한글 검색이 바로 되고, JVM·외부서버·trigram 제약 전부 없이 Vercel에서 그대로 동작.
  - `search/text_index.py` `TextIndex`: normalize(공백제거+소문자) → n-gram posting →
    질의도 n-gram으로 쪼개 교집합으로 후보 좁히고 substring 재확인으로 오탐 제거.
- **연동**(`web/samsam_app.py`): 데이터가 프로세스당 1회 로드(`_LC`)되므로 색인도 최초 사용 때
  1회 구축(`_indexes()`, 건물명·역명). `/api/buildings`의 건물명 검색(신규)·역 검색(기존)을
  모두 이 색인으로 태움. 실측: 색인 결과가 기존 순진 substring과 100% 동일(건물명 5203·역명 466).
- **프론트**(`templates/samsam.html`): 건물 인기 탭에 "건물명 검색" 입력 추가(역 검색 옆).
- 앞으로 텍스트 검색은 전부 `search/`를 거치게 확장 예정.

## 삼삼 스케줄 "빈값" 원인 확정 — 봇 계정 일일 한도 (fix/samsam-schedule-throttle)

실제 매물(102951)로 브라우저 vs 봇을 대조해 원인 확정.

- 미인증 `GET /v1/use-auth/rooms/{id}/schedules` → **401**(AUTH_002). 상세(`/rooms/{id}`)는 미인증도 200.
  즉 스케줄은 인증 필수.
- 사용자 로그인 브라우저: 같은 URL/파라미터로 `data.schedules` 정상(booking 다수). 봇: `SCSS_001`인데
  빈 배열 + `실패 0` → **봇은 인증엔 성공**(아니면 401)하는데 데이터만 빔.
- 사용자 요청 헤더(F12) 확인: `authorization` 헤더 **없음**(알파벳 순 accept-language→cache-control
  사이 공백). → **쿠키 인증**이고 Bearer 토큰 방식 아님. (Bearer 추가안은 폐기.)
- 타임라인: 7/2 오전 4,998건 갱신 성공 → 저녁부터 첫 요청부터 빈값 → **계정당 스케줄 조회 일일
  소프트한도**(초과 시 401 아닌 200+빈배열) 정황. 목록·상세는 같은 쿠키로 멀쩡 = 스케줄 엔드포인트 한정.

대응(저위험 2종 병행):
- `crawler.py`: 브라우저가 늘 보내는 `abid`(익명 UUID, 실행당 1개)·`client-language: ko` 헤더 추가 —
  봇 식별로 걸러지는 경우 대비(쿠키 인증엔 무영향).
- 워크플로: `SAMSAM_REFRESH_DAILY_LIMIT` 5000→3500 하향(한도 아래 여유). 공실 우선 쿨다운(#89)으로
  실제 대상도 줄어 상한엔 잘 안 닿음. 계정 한도는 하루면 리셋 예상 — 다음 실행에서 확인.
